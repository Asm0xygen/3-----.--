# Память проекта «Завхоз.рф»

**Фактическая сверка: 14 августа 2026.** Этот файл фиксирует подтверждённое состояние исходников; ТЗ и план описывают целевую реализацию, а не уже работающие возможности.

## Назначение и границы MVP

«Завхоз.рф» — прототип сервиса для работы с реестром основных средств и инвентаризацией. Целевой сценарий этапа 1: регистрация организации, помещения, управляемый импорт реестра ОС, размещение имущества, QR-метки, инвентаризация и одна итоговая ведомость.

Первый релиз не включает несколько пользователей и роли, бухгалтерский учёт и амортизацию, изменение стоимости обычным редактированием, 1С, ЭДО, электронную подпись, диагностику, списание, биллинг, административный контур, мобильное и офлайн-приложение. Технические правила и целевые API закреплены в `Docs/TECHNICAL_SPECIFICATION_STAGE_1.md`; при конфликте с `plans/IMPLEMENTATION_PLAN.md` приоритет у ТЗ.

## Структура репозитория

- `frontend/` — Vite + React + TypeScript + Tailwind: публичный сайт и отдельные статические демонстрационные входы.
- `backend/` — Express + TypeScript + Prisma; прототипное API и адаптер in-memory данных.
- `backend/prisma/schema.prisma` — текущая, устаревшая относительно ТЗ, модель PostgreSQL.
- `shared/` — старые общие TypeScript-интерфейсы прототипа; frontend и backend их сейчас не импортируют.
- `Docs/TECHNICAL_SPECIFICATION_STAGE_1.md` — нормативные требования этапа 1.
- `plans/IMPLEMENTATION_PLAN.md` — последовательность перехода от прототипа к этапу 1.
- `.agents/skills/` — локальные навыки агента; проектных инструкций `AGENTS.md`, `AGENTS.local.md`, `CLAUDE.md` и локальной `.harvi/` нет.

## Стек и команды

Корень — npm workspaces: `frontend`, `backend`, `shared`. Доступные команды:

```bash
npm install
npm run dev                    # backend и frontend через concurrently
npm run build                  # shared, backend, frontend
npm run start                  # backend
npm run prisma:generate --workspace=backend
npm run prisma:migrate --workspace=backend
```

Внутренние команды: `npm run dev --workspace=frontend` запускает Vite на `5173` с прокси `/api` на `http://localhost:3001`; `npm run dev --workspace=backend` запускает `tsx watch src/index.ts`. В репозитории нет lint- и test-скриптов и не обнаружены автоматические тесты.

## Реализовано сейчас

### Frontend

- Основной вход `frontend/src/main.tsx` рендерит публичный сайт. В `App.tsx` есть только маршруты `/` и `/about`; страницы не подключены к API.
- Публичная навигация ведёт только по лендингу, на `/about` и к почтовому запросу доступа; она не содержит ссылок на демонстрационные кабинеты.
- Vite также собирает изолированные входы `/admin-demo.html`, `/user-demo.html` и их альтернативы `/a9k4m7qx2vld.html`, `/p6w2r8tn5hcz.html`. Они рендерят статические `AdminDashboardDemo` и `UserDashboardDemo`, содержат демонстрационные цифры и явно отмечают отсутствие подключённых API и действий.
- Старый `frontend/src/components/Demo.tsx` — отдельная локальная имитация сценария с состоянием в браузере; основной `App.tsx` его не использует.

### Backend

- Вход: `backend/src/index.ts`; health-проверка — `GET /health`.
- Прототипные маршруты без версии: `POST /api/auth/register`, `POST /api/auth/login`; `GET /api/assets`, `GET /api/assets/:id`; `POST /api/import/os`, `POST /api/import/generate-qr`; `POST /api/inventory/start`, `POST /api/inventory/scan`, `GET /api/inventory/:id`; `GET /api/reports`, `GET /api/reports/:id`; набор `/api/gdpr/*`.
- Импорт принимает один файл до 10 МБ в памяти, разбирает только XLSX и CSV и сразу создаёт ОС. Генерация QR сохраняет data URL QR с инвентарным номером. Инвентаризация создаёт запись, сканирует объект по инвентарному номеру и меняет статус ОС; отчёты возвращаются JSON.
- При отсутствии `DATABASE_URL` или при шаблонной строке подключения используется in-memory `mockDb`; данные теряются при перезапуске. С PostgreSQL используется Prisma.

## Данные, изоляция и безопасность: фактическое состояние

- Текущая Prisma-схема содержит `User`, `Asset`, `Inventory`, `Scan`, `AuditLog`, `DataRequest`. У `Asset.inventoryNumber` глобальная уникальность, стоимость имеет тип `Float`; нет `Organization`, `Room`, `Session`, меток как отдельной сущности, движений, staged-импорта и tenant-полей `organizationId`.
- Следовательно, tenant-изоляция, привязка данных к организации и составные tenant-ограничения из ТЗ **не реализованы**.
- Регистрация требует согласие, хеширует пароль bcrypt и выдаёт JWT сроком семь дней. Вход также выдаёт JWT; аудит регистрации и входа записывается.
- Нет проверки JWT, общего middleware аутентификации, сессий, refresh/logout, отзыва токенов, ограничения частоты, строгой валидации запросов и защиты предметных маршрутов. `requireAuth` в GDPR-маршрутах проверяет только наличие заголовка `Bearer` и не задаёт `req.userId`; эти маршруты не готовы к использованию.
- CORS в production фиксирован на `https://3авхоз.рф`, вне production — `*` при `credentials: true`. Нет security headers и проверки обязательной конфигурации перед запуском. Не хранить секреты, токены, строки подключения и учётные данные в этом файле или в репозитории.

## Переход к этапу 1

ТЗ и план пока не реализованы. До изменения схемы нужно подтвердить наличие реальных данных PostgreSQL; до импорта и отчётов нужны три обезличенные реальные выгрузки и макет ведомости. Затем выполнять план по фазам: безопасная конфигурация и тестовый контур, целевая Prisma/OpenAPI/DTO-модель, проверяемая аутентификация и tenant-контекст, ядро учёта, staged-импорт, метки/инвентаризация/отчёт и только потом web-кабинет.

Новый целевой API имеет префикс `/api/v1`; старые `/api/*` и mock-режим не должны получать новые функции. Перед публичным или production-использованием обязательны миграции, тесты tenant-изоляции, защищённые сессии, ограничения API, production-конфигурация и эксплуатационная/юридическая проверка из плана.

## Правила изменений

- Не выдавать прототипные API, мок-данные и концептуальные показатели лендинга за рабочий сервис.
- Не ломать и не смешивать с приложением изолированные user/admin demos. Их URL — только демонстрационные входы, не механизм авторизации и не защита доступа; публичная навигация их не содержит.
- Сначала сверять реализацию с ТЗ, а при изменении общих контрактов искать использования в `frontend/`, `backend/` и `shared/`.
- Не изменять Prisma-модель как новую baseline без решения о реальных данных и безопасной стратегии миграции из плана.
