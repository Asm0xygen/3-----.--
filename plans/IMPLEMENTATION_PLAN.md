# План создания 3авхоз.рф с нуля

## 1. Статус и цель

- **Дата:** 2026-08-09
- **Статус:** план нового проекта; исходный код не используется как основа.
- **Цель первого релиза:** организация загружает реестр ОС, размещает имущество по помещениям, печатает метки, проводит инвентаризацию и получает ведомость результатов.

Первый релиз не включает мобильное приложение, биллинг, административную панель, диагностику, списание и ЭДО. Эти модули зависят от ядра и не должны задерживать проверку спроса.

## 2. Границы первого релиза

### Входит

1. Регистрация владельца организации и вход.
2. Карточка организации.
3. Реестр помещений.
4. Импорт XLS, XLSX и CSV с предварительным просмотром и сопоставлением колонок.
5. Реестр основных средств: поиск, фильтры, карточка, статус и привязка к помещению.
6. Перемещение имущества с историей.
7. Генерация и печать QR-меток.
8. Полная инвентаризация и инвентаризация выбранных помещений.
9. Фиксация результата: найдено, отсутствует, найдено вне ожидаемого помещения.
10. Экспорт инвентаризационной ведомости.
11. Журнал аудита критичных действий.

### Не входит

- роли и многопользовательская работа внутри организации;
- интеграция с 1С и автоматическая синхронизация;
- изменение стоимости и бухгалтерский учёт;
- мобильное приложение и офлайн-синхронизация;
- биллинг и приём платежей;
- административная панель;
- диагностика, списание, ЭДО и электронная подпись.

## 3. Решения до начала разработки

Эти решения обязательны. Без них нельзя проектировать БД и API.

1. **Tenant-изоляция:** одна организация на пользователя в первом релизе; `organizationId` есть у каждой предметной записи. Все запросы получают организацию только из проверенного токена, не из тела запроса.
2. **Повторный импорт:** ключ сопоставления — `inventoryNumber` в пределах организации. Импорт обновляет разрешённые бухгалтерские поля, не меняет помещение, QR-код, историю перемещений и результаты инвентаризаций. Пропавшие из выгрузки ОС помечаются для проверки, не удаляются.
3. **Статусы ОС:** `IN_USE`, `STORED`, `REPAIR`, `TO_WRITE_OFF`, `WRITTEN_OFF`. Статус изменяется только через разрешённые операции; `WRITTEN_OFF` нельзя вернуть без отдельного процесса восстановления.
4. **Инвентаризация:** QR содержит неизменяемый ID ОС и версию метки, не персональные данные. Скан вне ожидаемого помещения фиксируется отдельным результатом, не заменяет привязку ОС.
5. **Документы:** в первом релизе один шаблон инвентаризационной ведомости в PDF и XLSX. Юридическую форму утверждает заказчик до реализации.
6. **ПДн и инфраструктура:** сервер, PostgreSQL, объектное хранилище, резервные копии и логи размещаются в РФ. До публичного запуска утверждаются политика ПДн, соглашение и порядок обработки запросов субъектов ПД.

Результат этапа: утверждённый документ решений и примеры трёх реальных файлов выгрузки бухгалтерии.

## 4. Этап 0. Основание проекта

### Задачи

- [ ] Создать Git-репозиторий без старого прототипа и настроить `.gitignore`.
- [ ] Создать monorepo: `apps/web`, `apps/api`, `packages/contracts`.
- [ ] Зафиксировать Node.js, TypeScript, пакетный менеджер, линтер, форматтер и редакторские настройки.
- [ ] Настроить CI: установка зависимостей, проверка типов, линтинг, тесты, production-сборка.
- [ ] Подготовить `.env.example`, проверку обязательных переменных окружения и отдельные конфигурации dev/test/prod.
- [ ] Поднять локальные PostgreSQL и MinIO/S3-совместимое хранилище через Docker Compose.
- [ ] Создать healthcheck, структурированные логи и единый обработчик ошибок API.

### Критерий готовности

Чистый клон проекта проходит CI, запускает Web, API, PostgreSQL и создаёт пустую БД одной командой из документации.

## 5. Этап 1. Проектирование данных и контрактов

### Модель данных

- [ ] Создать ERD и словарь данных.
- [ ] Описать `Organization`, `User`, `Room`, `Asset`, `AssetLabel`, `Movement`, `ImportJob`, `ImportRow`, `Inventory`, `InventoryItem`, `AuditLog`.
- [ ] Для денег использовать `Decimal`, для статусов — enum.
- [ ] Добавить `organizationId` к предметным сущностям и составные уникальные индексы, включая `@@unique([organizationId, inventoryNumber])`.
- [ ] Определить каскадное удаление, архивирование и сроки хранения данных.
- [ ] Создать начальную Prisma-миграцию и тестовые данные для двух организаций.

### API

- [ ] Описать OpenAPI-контракт до реализации маршрутов.
- [ ] Зафиксировать ошибки, пагинацию, сортировку, фильтры и формат дат.
- [ ] Описать операции: регистрация, помещения, импорт, ОС, перемещения, метки, инвентаризация, экспорт.
- [ ] Сгенерировать или вручную поддерживать общие типы API в `packages/contracts`.

### Критерий готовности

Есть ERD, миграция, OpenAPI и контрактные тесты. Тестовые данные двух организаций не пересекаются ни одним запросом.

## 6. Этап 2. Безопасность и доступ

### Задачи

- [ ] Реализовать регистрацию, вход, обновление сессии, выход и смену пароля.
- [ ] Хешировать пароли Argon2id или bcrypt с безопасными параметрами.
- [ ] Ввести короткоживущий access token и защищённый refresh token в `HttpOnly`, `Secure`, `SameSite` cookie.
- [ ] Реализовать middleware проверки токена и tenant-контекста.
- [ ] Защитить все предметные маршруты авторизацией и tenant-фильтрами.
- [ ] Добавить rate limit для входа, регистрации, импорта и экспорта.
- [ ] Добавить CORS по разрешённым доменам, security headers, ограничение тела запроса и валидацию входных данных.
- [ ] Писать аудит входа, импорта, создания, изменения, перемещения, инвентаризации и экспорта.

### Критерий готовности

Попытки доступа к данным другой организации возвращают `403` или `404`; JWT без подписи, просроченный токен и поддельный `organizationId` не дают доступ.

## 7. Этап 3. Ядро учёта имущества

### Задачи

- [ ] Реализовать CRUD организации и помещений.
- [ ] Реализовать CRUD ОС: создание, просмотр, редактирование разрешённых полей, архивирование, поиск и фильтры.
- [ ] Реализовать смену помещения только через операцию перемещения.
- [ ] Хранить историю перемещений: дата, источник, назначение, причина, инициатор.
- [ ] Реализовать отображение реестра ОС и карточки ОС в Web.
- [ ] Добавить серверную и клиентскую валидацию инвентарного номера, стоимости, дат и статусов.

### Критерий готовности

Пользователь создаёт помещения, добавляет ОС, перемещает ОС и видит неизменяемую историю операций. Данные второй организации недоступны.

## 8. Этап 4. Управляемый импорт

### Задачи

- [ ] Поддержать XLS, XLSX и CSV; ограничить тип и размер файла.
- [ ] Не хранить оригинальный файл после завершения импорта.
- [ ] Сохранять временные строки `ImportRow` до подтверждения или отмены операции.
- [ ] Реализовать анализ заголовков, сопоставление колонок, предпросмотр и валидацию строк.
- [ ] Показать пользователю новые, обновляемые, конфликтные и ошибочные строки до подтверждения.
- [ ] Выполнять импорт транзакционно; создать журнал результата с количеством строк и ошибками.
- [ ] Реализовать правила повторного импорта из раздела 3.

### Критерий готовности

Три согласованных файла выгрузки проходят импорт. Ошибочная строка не повреждает существующие данные. Повторный импорт не стирает размещение, историю и инвентаризацию.

## 9. Этап 5. Метки и инвентаризация

### Задачи

- [ ] Генерировать QR-метку для ОС; поддержать массовую подготовку к печати.
- [ ] Создать печатный лист меток в PDF.
- [ ] Создать полную и комнатную инвентаризацию.
- [ ] При старте зафиксировать список проверяемых ОС в `InventoryItem`.
- [ ] Реализовать сканирование через камеру браузера и ручной ввод как резервный сценарий.
- [ ] Определять результат сканирования: найдено, вне ожидаемого помещения, повторное сканирование, неизвестная метка.
- [ ] Завершать инвентаризацию с расчётом отсутствующих ОС; не менять статус ОС автоматически.
- [ ] Экспортировать ведомость результатов в PDF и XLSX.

### Критерий готовности

Пользователь печатает метки, проводит инвентаризацию одного помещения, фиксирует все четыре сценария сканирования и скачивает ведомость.

## 11. Этапы после пилота

Реализуются только после подтверждённого использования ядра.

1. Комиссии, диагностика и документы списания.
2. Многопользовательский режим и роли.
3. Биллинг и платёжный провайдер.
4. Административная панель.
5. Мобильное приложение; офлайн-режим проектируется отдельно с правилами конфликтов синхронизации.
6. Интеграции с 1С, ЭДО и электронная подпись.

## 12. Главные риски и контроль

| Риск | Контроль |
|---|---|
| Неверные правила повторного импорта | Утвердить до модели БД и проверить реальными выгрузками. |
| Утечка данных между организациями | Tenant-контекст в middleware, обязательные фильтры, тесты двух организаций. |
| Расширение границ MVP | Продуктовый backlog для функций после пилота; не добавлять их в первый релиз. |
| Ошибки данных при импорте | Предпросмотр, staging-строки, транзакции, журнал результата. |
| Непригодные печатные формы | Утвердить шаблоны с заказчиком до реализации экспорта. |
| Неготовность к обработке ПДн | Юридические документы, размещение в РФ, аудит, резервное копирование до публичного запуска. |
