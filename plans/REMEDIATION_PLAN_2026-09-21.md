# План исправления прототипа и перехода к этапу 1

**Дата:** 21 сентября 2026 года  
**Основания:** `reports/critique-consensus-2026-09-21.md`, `code-quality-review.json`, `PROJECT_MEMORY.md`, `Docs/TECHNICAL_SPECIFICATION_STAGE_1.md`  
**Статус:** фаза 0 завершена 22 сентября 2026 года; выполняется фаза 1.1.

## 1. Цель и границы

Цель — безопасно заменить прототипное API этапом 1: регистрация организации, помещения, управляемый импорт ОС, реестр, QR-метки, инвентаризация и итоговая ведомость.

В этап 1 **не входят** роли и несколько пользователей, административный контур, WebAuthn, биллинг, 1С, ЭДО, списание, мобильное и offline-приложение. Эти пункты из consensus-отчёта не должны попасть в текущий объём работ.

Новый функционал создаётся только под `/api/v1`. Прототипные `/api/*` и `mockDb` не расширяются; до удаления их следует оставить только для явно выделенной локальной демонстрационной конфигурации.

## 2. Блокеры до начала разработки

## 3. Принятые технические решения

1. **Хранилище данных:** PostgreSQL + Prisma остаются. Raw SQL используется точечно только для невозможных или неэффективных Prisma-запросов после профилирования.
2. **Изоляция:** shared database, каждая предметная запись содержит `organizationId`; он извлекается только из проверенной серверной сессии.
3. **Сессии:** короткоживущий JWT access token и серверная `Session` для refresh token. Refresh token хранится в `HttpOnly`, `Secure`, `SameSite` cookie, в БД хранится только хеш.
4. **Деньги и даты:** `Decimal(15,2)` и API-строки для денег; даты учёта — `YYYY-MM-DD`, время — ISO 8601 UTC.
5. **Валидация:** единые Zod-схемы для тела, параметров и query-параметров; ошибки в контрактном формате ТЗ.
6. **Тестирование:** отдельная PostgreSQL БД для интеграционных тестов. In-memory адаптер нельзя использовать для доказательства tenant-изоляции, миграций и транзакций.
7. **Наблюдаемость:** структурированный лог без токенов, паролей, содержимого импортов и полного IP в обычных access-логах.

## 4. Последовательность реализации

### Фаза 0 — воспроизводимая среда и тестовый контур

**Цель:** до изменения бизнес-логики сделать сборку, проверку конфигурации и тестирование обязательными.

#### Шаг 0.1. Зафиксировать инструменты и команды

1. Выбрать и добавить тестовый раннер для TypeScript, библиотеку HTTP-тестов, ESLint и форматтер.
2. Добавить scripts `lint`, `typecheck`, `test`, `test:unit`, `test:integration` в корневой и workspace `package.json`.
3. Настроить CI: чистая установка, `typecheck`, `lint`, unit/integration-тесты, production build и `git diff --check`.
4. Описать Node.js-версию, локальный запуск PostgreSQL и команды проверки в `README.md`.

**Затрагиваемые файлы:** `package.json`, `backend/package.json`, `frontend/package.json`, новые конфигурации тестов/линтера, `README.md`, CI-конфигурация.

**Проверка готовности:** чистый клон проходит установку, `npm run build`, typecheck, lint и пустой тестовый набор в CI.

#### Шаг 0.2. Конфигурация и режимы запуска

1. Создать `backend/src/config/env.ts` с типизированной проверкой переменных среды до импорта маршрутов.
2. Обязательные значения: `JWT_SECRET`, `DATABASE_URL` в production, allowlist CORS, безопасные cookie-параметры, лимиты загрузки.
3. В `backend/.env.example` оставить только placeholder-значения и список переменных без секретов.
4. В `backend/src/db/index.ts` заменить неявное условие `!DATABASE_URL` на явный `USE_MOCK=true` исключительно для local demo.
5. Если `NODE_ENV=production` и БД/секрет отсутствуют или недоступны — завершать процесс с понятным сообщением.
6. Проверить `.gitignore` и Git-историю на секреты; при обнаружении отозвать и заменить ключи, затем согласовать безопасную очистку истории отдельно.

**Проверка готовности:** production-процесс не стартует без обязательной конфигурации; development не включает mock без `USE_MOCK=true`; проверка истории документирует результат без публикации секретов.

#### Шаг 0.3. Базовая HTTP-безопасность и ошибки

1. Создать `backend/src/middleware/error-handler.ts`, `request-id.ts` и тип `ApiError`.
2. Ввести единый ответ: `{ error: { code, message, fields? } }` и статусы из ТЗ.
3. Добавить ограничение `express.json({ limit: ... })`, request ID, readiness endpoint с проверкой БД и безопасный логгер.
4. Установить security headers, CORS allowlist из среды и корректный `trust proxy` только для согласованной инфраструктуры.
5. Не логировать `Authorization`, cookie, пароль, refresh token, тело импорта; IP либо исключить из access-лога, либо хранить только в минимальном audit-контексте.

**Проверка готовности:** ошибки валидации имеют единый формат; CORS не использует `*` совместно с credentials; логи не содержат секретных заголовков.

### Фаза 1 — контракт, новая схема и безопасная миграция

**Цель:** закрепить API и модель до переноса функций из прототипа.

#### Шаг 1.1. Подготовить контракт API и DTO

1. Создать OpenAPI 3.0 в `backend/openapi/` по разделу 5 ТЗ: пути `/api/v1`, схемы, pagination, ошибки, security requirements.
2. Создать DTO и общие enum в `shared/`; не экспортировать Prisma-модели, хеши паролей и токены.
3. Добавить Zod-схемы, согласованные с OpenAPI; обработчик преобразует ошибки Zod в формат ТЗ.
4. Зафиксировать правила `404` для чужих ресурсов и запрет входящего `organizationId` в предметных командах.

**Проверка готовности:** OpenAPI, DTO, Zod-схемы и примеры запросов не расходятся; frontend может генерировать или типизировать клиент по контракту.

#### Шаг 1.2. Спроектировать и реализовать Prisma-схему

1. После B1 заменить прототипные модели в `backend/prisma/schema.prisma` сущностями: `Organization`, `User`, `Session`, `Room`, `Asset`, `AssetLabel`, `Movement`, `ImportJob`, `ImportRow`, `Inventory`, `InventoryRoom`, `InventoryItem`, `AuditLog`.
2. Добавить enum из ТЗ: статусы ОС, импорта, инвентаризации и позиций; исключить статусы списания из первого релиза.
3. Ввести `organizationId` в каждую предметную сущность и целевые индексы, включая `@@unique([organizationId, inventoryNumber])`, `@@unique([inventoryId, assetId])`, индексы фильтрации реестра.
4. Заменить `Asset.cost Float` на `Decimal(15,2)`; разделить `accountingDate` и `DateTime` поля; заменить удаление на `isArchived`/`archivedAt` для ОС и комнат.
5. Добавить ограничения отношений и сервисные проверки, не позволяющие связать актив, комнату, метку, импорт или инвентаризацию разных организаций.
6. Создать фикстуры двух организаций с одинаковым `inventoryNumber` у разных tenant и конфликтом внутри одной организации.

**Стратегия миграции:**
- **Если реальных данных нет:** создать новую baseline-миграцию и отдельно убрать устаревшие таблицы прототипа.
- **Если реальные данные есть:** backup → инвентаризация источника → mapping → миграция на копии → сверка количеств/сумм → rollback-план → только потом production.

**Проверка готовности:** схема применяется на пустой и тестовой БД; две организации могут использовать одинаковый инвентарный номер, но одна — нет; финансы сериализуются строкой.

### Фаза 2 — аутентификация, сессии и tenant-барьеры

**Цель:** устранить незащищённые маршруты до переноса бизнес-функций.

#### Шаг 2.1. Реализовать auth middleware и сессии

1. Создать `backend/src/middleware/auth.ts` с безопасным разбором Bearer, `jwt.verify`, проверкой issuer/audience при их введении и установкой типизированного `req.auth`.
2. Создать `requireOrganizationContext`: получать `userId` и `organizationId` только из проверенной сессии/токена.
3. Реализовать `/api/v1/auth/register` одной транзакцией: нормализация email, проверка пароля и ИНН, `consent: true`, создание Organization, User, Session, AuditLog. При отсутствии согласия вернуть `422`.
4. Реализовать login, refresh с rotation, logout; access token сделать короткоживущим, refresh token сохранять как hash и отзывать на logout.
5. Добавить `Cache-Control: no-store` на auth-ответы; возвращать одинаковую ошибку для неизвестного email и неверного пароля.
6. Старые `backend/src/routes/auth.ts` и `gdpr.ts` не исправлять частично как новую платформу: заменить после появления v1 и удалить/изолировать legacy маршруты.

#### Шаг 2.2. Защитить все предметные маршруты

1. Подключать `requireAuth` и tenant-context перед каждым `/api/v1` ресурсом: организация, комнаты, ОС, импорт, метки, инвентаризации, отчёты.
2. Во всех чтениях, обновлениях, архивировании и экспортах добавлять `organizationId: req.auth.organizationId` в условия выборки.
3. При обращении к чужому идентификатору возвращать `404`, а не `403`.
4. Удалить публичный доступ, существующий в `backend/src/routes/assets.ts`, `inventory.ts`, `reports.ts`; не переносить прототипную логику без tenant-фильтров.
5. Добавить rate limits для register/login/refresh, upload, генерации документов и scan.

#### Шаг 2.3. Добавить минимальный тестовый барьер безопасности

1. Тесты auth: токен отсутствует, подделан, просрочен, отозван; login не раскрывает существование пользователя; logout отзывает refresh session.
2. Контрактные tenant-тесты ТЗ №1–4 и №11: пользователь A не читает/изменяет/архивирует/экспортирует данные B; `organizationId` клиента отклонён/игнорирован; уникальность номера tenant-ограничена; consent без создания данных возвращает `422`.
3. Тесты выполнять против PostgreSQL.

**Проверка готовности фазы:** ни один защищённый v1-маршрут не доступен с произвольным Bearer; все tenant-тесты проходят.

### Фаза 3 — организация, помещения, реестр ОС и движения

1. Реализовать `GET/PATCH /api/v1/organization` с whitelist редактируемых полей.
2. Реализовать CRUD-команды комнат: list/create/get/patch/archive; архив запрещён при наличии неархивных ОС.
3. Реализовать реестр ОС: пагинация (`page`, `pageSize <= 100`), поиск, фильтры `roomId`, `status`, `importState`, `includeArchived`.
4. Реализовать карточку и создание ОС вручную; обычный PATCH разрешает только `name`, `serialNumber`, допустимый `status`.
5. Реализовать перемещение одной транзакцией: проверить tenant актива/комнат, создать неизменяемый `Movement`, изменить `Asset.roomId`, записать AuditLog.
6. Реализовать архив ОС без физического удаления; запретить операцию для ОС, участвующей в активной инвентаризации.
7. Добавить тесты переходов статуса, ограничений архивирования, истории перемещений и tenant-фильтров.

**Проверка готовности:** владелец одной организации создаёт помещение, ОС, перемещает и архивирует их; не может изменить `roomId`, стоимость или дату учёта обычным PATCH.

### Фаза 4 — staged-импорт и повторная загрузка реестра

**Предусловия:** получены B2 и B3.

1. Заменить `backend/src/routes/import.ts` v1 workflow: `POST /imports` → `PUT /mapping` → `POST /validate` → `GET /rows` → `POST /confirm` или `/cancel`.
2. При upload проверять разрешённые расширения/сигнатуры, 10 МБ и 50 000 строк; вычислять SHA-256; хранить только метаданные и `ImportRow`, исходный файл удалять после разбора.
3. Использовать устойчивый CSV-парсер с BOM и экранированными кавычками; XLS/XLSX обрабатывать через согласованную библиотеку.
4. Нормализовать данные строго по ТЗ: trim, допустимые даты, деньги с пробелами/запятыми в `Decimal`, обязательные `inventoryNumber` и `name`.
5. Классифицировать каждую строку `CREATE`, `UPDATE`, `SKIP`, `CONFLICT`, `INVALID`; дубликаты одного номера внутри файла — `CONFLICT`.
6. Разрешать confirm только при нулевых `invalidRows` и `conflictRows`.
7. Выполнять confirm одной транзакцией: менять только бухгалтерские поля; не менять room, метки, движения, архивирование и завершённые инвентаризации; помечать отсутствующие ОС как `MISSING_FROM_LAST_IMPORT`.
8. Создавать AuditLog и счётчики результата; реализовать cancellation, expiration и очистку временных строк.
9. Добавить тесты ТЗ №5–6, а также: неверная дата, отрицательная стоимость, дубликат, предел строк и откат транзакции.

**Проверка готовности:** ошибочная/конфликтная строка не меняет ОС; подтверждение изменяет реестр атомарно; три согласованные выгрузки проходят workflow.

### Фаза 5 — QR-метки, инвентаризация и ведомость

**Предусловие:** получен B4.

1. Реализовать версионированный `AssetLabel`: криптографически случайный непрозрачный token, отзыв прошлой активной метки и AuditLog в одной транзакции.
2. QR содержит только `asset-label:<token>` или URL с token; не включать инвентарный номер или организацию.
3. Реализовать печать PDF по утверждённому макету; не сохранять QR как data URL в `Asset`.
4. Реализовать инвентаризацию `FULL`/`ROOMS` в статусе `DRAFT`; для `ROOMS` сохранять `InventoryRoom`.
5. `start` создаёт неизменяемый snapshot `InventoryItem`; после старта изменения реестра не меняют состав проверки.
6. `scan` проверяет tenant, активность метки, принадлежность позиции snapshot и отсутствие повторного скана; сопоставляет `expectedRoomId`/`actualRoomId` и возвращает `FOUND`/`MISPLACED`.
7. `complete` переводит только `PENDING` в `MISSING`, считает итоги и не меняет `Asset.status` или `roomId`.
8. Формировать PDF и XLSX из одной модели данных; добавить пагинацию позиций и экспорт.
9. Добавить тесты ТЗ №7–10 и №12, включая чужую/отозванную метку, повторный scan (`409`) и комнаты.

**Проверка готовности:** инвентаризация комнаты покрывает FOUND, MISPLACED, MISSING и неизвестную метку; PDF/XLSX совпадают с API-итогами и утверждённым образцом.

### Фаза 6 — подключение web-кабинета

1. Не подключать `frontend/src/pages/Auth.tsx` к прототипному API. После утверждения B6 подключить его к v1-клиенту.
2. Создать типизированный API client: access token в памяти, refresh через защищённую cookie, общий обработчик `401`, единый разбор API-ошибок.
3. Вынести client-side валидаторы email/ИНН/форм из `Auth.tsx` в `shared/` или frontend-утилиты; серверные правила остаются источником истины.
4. Добавить защищённые маршруты для организации, комнат, реестра, карточки ОС, импорта, меток и инвентаризации.
5. Для каждого экрана реализовать loading, empty, validation error, network error, forbidden/session-expired.
6. Импортный UI строить по шагам upload → mapping → validate → preview → confirm/cancel, без необратимого создания ОС после upload.
7. Для инвентаризации обязательный первый сценарий — ручной ввод; камера добавляется только после отдельного выбора и тестирования библиотеки.
8. Статические `AdminDashboardDemo`, `UserDashboardDemo` и `Demo.tsx` не считать продуктовым UI. Изолировать или удалить неиспользуемую demo-логику только после замены целевыми экранами.
9. Добавить E2E: регистрация → комнаты → импорт → перемещение → метка → инвентаризация → ведомость.

**Проверка готовности:** пользователь проходит полный сценарий без mock-данных; UI не передаёт `organizationId`; токены не записываются в localStorage/sessionStorage.

### Фаза 7 — production readiness и пилот

1. Выполнить контрактные тесты всех 12 проверок ТЗ, unit-тесты нормализации/статусов/меток и интеграционные API-тесты с PostgreSQL.
2. Нагрузочно проверить 50 000 строк импорта, пагинацию реестра и завершение инвентаризации; целевой бюджет для списка 1 000 ОС установить до пилота и измерять на staging.
3. Профилировать запросы: вместо текущих `findMany()` в `inventory.ts` и `reports.ts` использовать tenant-scoped запросы, `include`/Map или агрегаты. Оптимизацию делать в целевой v1 реализации, не расширяя legacy.
4. Добавить HTTPS/HSTS на ingress, CORS allowlist, rate limit, мониторинг доступности/ошибок и резервное копирование с тестовым восстановлением.
5. Сгенерировать и опубликовать OpenAPI, runbook развёртывания/rollback/инцидентов.
6. Провести отдельную юридическую и эксплуатационную проверку ПДн, затем ограниченный пилот на одной организации.

**Проверка готовности:** CI зелёный; две организации доказательно изолированы; backup восстановлен в отдельной среде; пилотный пользователь завершает сценарий без прямой помощи разработчика.

## 6. Реестр рисков и контроль

| Риск | Контроль |
|---|---|
| Потеря реальных данных при миграции | Не менять Prisma baseline до B1; backup, миграция на копии, сверка и rollback |
| Межтенантная утечка | tenant middleware, фильтр в каждом запросе, тестовый набор двух организаций и `404` для чужих ID |
| Расширение MVP | Любой пункт вне ТЗ этапа 1 переносить в backlog; не добавлять роли, admin, 1С или mobile |
| Некорректный импорт | Три реальные обезличенные фикстуры, staging, транзакционный confirm, тесты rollback |
| Слабая эксплуатационная готовность | production-конфигурация, мониторинг, backup-restore test, audit без секретов |
| Несогласованность frontend/backend | OpenAPI и DTO до подключения UI; контрактные тесты в CI |

## 7. Итоговые контрольные точки

1. **КТ-0:** инструменты, PostgreSQL test DB и production-safe configuration готовы.
2. **КТ-1:** OpenAPI/DTO/Prisma-схема согласованы, миграция безопасно проверена.
3. **КТ-2:** проверяемая аутентификация, refresh/logout и tenant-изоляция доказаны тестами.
4. **КТ-3:** организация, помещения, ОС и движения работают без физического удаления.
5. **КТ-4:** staged-импорт проверен тремя реальными обезличенными выгрузками.
6. **КТ-5:** QR, инвентаризация и ведомость сверены с утверждённым макетом.
7. **КТ-6:** браузерный end-to-end сценарий, безопасность, backup-restore и пилот завершены.

## 8. Что не делать в качестве «быстрой заплатки»

- Не ограничиваться добавлением `jwt.verify` в устаревший `gdpr.ts`, оставляя остальные `/api/*` маршруты публичными.
- Не добавлять `organizationId` из тела HTTP-запроса и не доверять ему.
- Не менять `schema.prisma` без решения B1 и проверяемой миграционной стратегии.
- Не продолжать прямой импорт, который частично пишет данные до валидации и транзакционного confirm.
- Не использовать `Float` для стоимости и не возвращать деньги JavaScript number.
- Не включать mock БД по отсутствию `DATABASE_URL` в production.
- Не подключать текущую страницу регистрации к прототипному API до юридически утверждённых текстов и защищённых сессий.
