# Проектирование регистрации, авторизации и административного доступа

**Статус:** проектное решение, не реализовано.  
**Дата:** 14 августа 2026 года.  
**Область:** новый API `/api/v1`, будущие web-кабинеты и production-развёртывание.

## 1. Назначение и границы

Документ задаёт целевую безопасную модель для:

1. регистрации владельца организации и его входа в пользовательский кабинет;
2. управления пользовательскими сессиями, восстановлением доступа и подтверждением email;
3. изоляции данных организаций в API;
4. отдельного входа сотрудников платформы в административный контур.

`Администратор платформы` и `владелец организации` — разные типы субъектов:

| Субъект | Назначение | Место входа | Хранилище учётных данных |
|---------|------------|-------------|--------------------------|
| Владелец организации | Ведёт данные только своей организации | `https://app.3авхоз.рф` | `User`, `Session` |
| Администратор платформы | Обслуживает платформу в пределах выданных полномочий | `https://admin.3авхоз.рф` | `AdminAccount`, `AdminSession`, `AdminWebAuthnCredential` |

Учётная запись владельца **не получает** доступ к админке по флагу `isAdmin`, а учётная запись администратора не становится пользователем организации. Даже при одинаковом email это независимые идентичности, с отдельными паролями, сессиями, ключами и аудитом.

Административный контур не входит в утверждённые границы этапа 1 по текущему ТЗ. Этот документ описывает его безопасную реализацию после отдельного решения владельца продукта; до такого решения не следует добавлять админ-маршруты, роли или скрытые обходы tenant-изоляции.

## 2. Исходное состояние и обязательный переход

Текущие `/api/auth/*`, единый JWT на семь дней, in-memory режим и `admin-demo.html` являются прототипом. Они не соответствуют этой схеме и не могут использоваться в production.

Новая реализация должна:

- существовать только под `/api/v1` и `/api/admin/v1`;
- не расширять старые `/api/*` новыми возможностями;
- не включаться при `DATABASE_URL` отсутствует или указывает на шаблонное значение;
- быть введена после решения о наличии реальных данных, резервной копии и миграционного плана из `plans/IMPLEMENTATION_PLAN.md`;
- оставить `admin-demo.html` и альтернативные demo-входы демонстрационными страницами, не связанными с реальной авторизацией.

## 3. Топология и границы доверия

### 3.1. Целевая схема размещения

```text
Публичный сайт       https://3авхоз.рф
Кабинет организации  https://app.3авхоз.рф
Админ-контур         https://admin.3авхоз.рф

app.3авхоз.рф/api/v1/*          -> reverse proxy -> backend /api/v1/*
admin.3авхоз.рф/api/admin/v1/*  -> reverse proxy -> backend /api/admin/v1/*
```

В production backend не публикуется напрямую в интернет. Reverse proxy принимает TLS, разрешает только известные `Host`, передаёт корректный адрес клиента от доверенного прокси и направляет каждый контур только на разрешённый набор путей.

Имена хостов настраиваются через переменные окружения `APP_ORIGIN` и `ADMIN_ORIGIN`. Для IDN-домена фактическая DNS-конфигурация использует его корректное каноническое представление; сравнение `Origin`, `Host` и WebAuthn RP ID выполняется со значением из проверенной production-конфигурации, а не с произвольным заголовком клиента.

Разные origin позволяют использовать host-only cookies с префиксом `__Host-`. Cookie пользователя не отправляется на `admin.3авхоз.рф`, а cookie администратора не отправляется на `app.3авхоз.рф`.

### 3.2. Инварианты безопасности

1. API получает `userId`, `sessionId` и `organizationId` только из проверенной серверной сессии, а не из тела, query-параметров или заголовков клиента.
2. Каждая предметная выборка и каждая мутация ограничены `organizationId` из контекста запроса. Чужой объект отвечает `404`, а не `403`.
3. Пароли, refresh token, session token, одноразовые ссылки, WebAuthn challenge, приватные ключи и строки подключения никогда не пишутся в логи, аудит, URL query, frontend state или репозиторий.
4. Админские маршруты не принимают пользовательские access token, а пользовательские маршруты не принимают админские cookie и сессии.
5. Полномочия проверяются на сервере для каждого действия. Скрытие кнопки в UI не является контролем доступа.

## 4. Пользовательский контур

### 4.1. Регистрация и подтверждение email

Форма регистрации принимает `email`, `password`, `name`, `inn`, `consent: true` и версию документов, с которыми пользователь согласился. Email нормализуется до lowercase после проверки синтаксиса; ИНН и имя проходят строгую серверную валидацию.

Последовательность:

1. `POST /api/v1/auth/register` создаёт в одной транзакции `Organization` и `User` со статусом `PENDING_EMAIL_VERIFICATION`, `consentAt` и записью доказательства согласия.
2. Сервер создаёт криптографически случайный одноразовый токен подтверждения. В БД хранится только его HMAC-хеш, срок действия — 24 часа.
3. Письмо содержит ссылку вида `https://app.3авхоз.рф/verify-email#token=<token>`. Фрагмент после `#` не отправляется веб-серверу и не попадает в access log. Страница передаёт токен только в теле `POST /api/v1/auth/verify-email`.
4. После успешной проверки токен помечается использованным, `emailVerifiedAt` заполняется, пользователь становится `ACTIVE`, создаётся первая пользовательская сессия и аудит.
5. Неподтверждённые регистрации не имеют API-доступа и автоматически удаляются либо обезличиваются по утверждённому сроку хранения.

Повторная регистрация или запрос нового письма возвращает нейтральный ответ `202`, не раскрывая наличие активной учётной записи. Отправка ограничена по IP и по нормализованному email.

### 4.2. Пароль

Пароль хранится только как `Argon2id`-хеш. Начальные параметры: память не менее 19 MiB, не менее двух итераций и один поток; перед production они измеряются на целевом сервере и фиксируются в конфигурации. Вход успешен и для старого хеша только на время миграции: при первом успешном входе он немедленно заменяется на Argon2id.

Правила ввода:

- минимум 12 символов для владельца организации, минимум 15 — для администратора;
- максимум 128 символов после нормализации, без произвольного обрезания;
- без обязательных классов символов и без периодической смены без признаков компрометации;
- отказ для известных скомпрометированных и распространённых паролей по согласованному локальному набору либо прошедшей проверку приватности службе;
- пароль не возвращается в ошибках и не включается в telemetry.

### 4.3. Токены и сессия пользователя

После `login`, `verify-email` или `refresh` клиент получает короткоживущий access token в JSON-ответе. Он хранится только в памяти приложения и передаётся в `Authorization: Bearer <token>`.

| Артефакт | Формат и хранение | Срок | Назначение |
|----------|-------------------|------|------------|
| Access token | Подписанный `ES256` или `EdDSA` JWT; только в памяти браузера | 5 минут | Доступ к `/api/v1` |
| Refresh token | Случайное значение не менее 256 бит; в БД HMAC-хеш | До 30 суток с абсолютным истечением | Получение нового access token |
| Refresh cookie | `__Host-user_refresh`; `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/` | Не дольше refresh session | Передача refresh token браузером |

JWT содержит только `iss`, `aud`, `sub` (идентификатор пользователя), `sid` (идентификатор сессии), `typ=USER_ACCESS`, `jti`, `iat` и `exp`. В нём нет email, ИНН, организации, ролей, паролей или персональных данных. Проверка фиксирует разрешённый алгоритм, `issuer`, `audience`, тип и время жизни; алгоритм из заголовка токена не выбирается динамически.

При обработке access token сервер дополнительно проверяет, что `Session` не отозвана, не истекла, принадлежит активному пользователю, а `organizationId` извлекает из серверной записи пользователя. Короткий JWT ограничивает окно до проверки отзыва; кэш таких проверок допустим только с TTL не длиннее access token и с немедленной инвалидизацией при отзыве.

#### Rotation refresh token

`POST /api/v1/auth/refresh` выполняется одной транзакцией:

1. находит активную сессию по HMAC-хешу токена;
2. помечает старый token использованным и отозванным;
3. создаёт новую `Session` в той же `sessionFamilyId`;
4. задаёт новую cookie и возвращает новый access token с `Cache-Control: no-store`.

Повторное использование уже заменённого token означает возможную кражу. Сервер отзывает всю семью сессий пользователя, записывает событие безопасности и требует новый вход. Конкурирующие refresh-запросы обрабатываются атомарно: успешным может стать только один из них.

### 4.4. Вход, выход и восстановление доступа

- `POST /api/v1/auth/login` всегда возвращает одинаковую ошибку `401 INVALID_CREDENTIALS` для неизвестного email, неверного пароля, неподтверждённого или заблокированного пользователя. После правильного пароля неподтверждённому пользователю допускается только нейтральное предложение переотправить письмо.
- `POST /api/v1/auth/logout` отзывает текущую session и очищает cookie с теми же атрибутами.
- `POST /api/v1/auth/logout-all` требует действующую сессию и повторное подтверждение пароля; отзывает все семейства сессий пользователя.
- `POST /api/v1/auth/password-reset/request` всегда отвечает `202`. Одноразовый токен сброса действует 15 минут, хранится только в виде HMAC-хеша и одноразово используется через `POST /api/v1/auth/password-reset/confirm`.
- После сброса пароля меняется пароль, отзываются все пользовательские сессии, использованные токены аннулируются, отправляется уведомление на email и создаётся аудит.
- Смена email и пароля требует недавней повторной аутентификации. Новый email не становится активным до отдельного подтверждения.

Пользовательский кабинет должен показывать активные сессии с ограниченными данными о браузере и времени, позволять завершить отдельную сессию и все сессии сразу.

## 5. Отдельный административный контур

### 5.1. Вход и многофакторная защита

Реальный вход администратора расположен только по адресу `https://admin.3авхоз.рф/login`; на публичном сайте и в пользовательском кабинете ссылки на него не обязательны. Сокрытие ссылки не считается защитой.

Вход состоит из двух обязательных факторов:

1. пароль администратора;
2. WebAuthn/passkey с обязательной проверкой присутствия и верификацией пользователя (`userVerification: required`).

Последовательность:

1. `POST /api/admin/v1/auth/login` проверяет email и пароль, создаёт одноразовую `AdminLoginTransaction` сроком на 5 минут и выдаёт параметры WebAuthn assertion. Временная cookie не является аутентифицированной сессией.
2. Браузер вызывает WebAuthn только с RP ID и origin, равными `admin.3авхоз.рф` из production-конфигурации.
3. `POST /api/admin/v1/auth/webauthn/verify` проверяет challenge, origin, RP ID, credential, подпись, флаги UV и счётчик. При успехе создаётся `AdminSession`.
4. Сервер устанавливает cookie `__Host-admin_session` с атрибутами `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`; JavaScript не получает админский bearer token.

`AdminSession` действует не более 8 часов и завершается после 15 минут бездействия. Критичные операции требуют свежего подтверждения WebAuthn не старше 10 минут: управление администраторами, отзыв доступа, экспорт аудита, раскрытие данных конкретной организации и экстренный доступ.

Для одной учётной записи регистрируются минимум два независимых passkey: основной и резервный. Вход только по паролю, email-коду или SMS запрещён. Потеря всех passkey восстанавливается только по документированной ручной процедуре двумя уполномоченными сотрудниками безопасности с уведомлением, задержкой и полным аудитом; автоматического обхода MFA нет.

### 5.2. Создание и прекращение админских учётных записей

Открытой регистрации администратора нет. Администратора создаёт защищённая операционная процедура:

1. контролируемый CLI или миграция создаёт `AdminAccount` в статусе `INVITED` и одноразовое приглашение с коротким сроком действия;
2. приглашённый задаёт пароль и регистрирует два passkey до активации;
3. назначение роли требует отдельного подтверждённого процесса и записывается в аудит;
4. при увольнении, подозрении на компрометацию или смене роли аккаунт блокируется, все `AdminSession` отзываются сразу, а активные экстренные доступы завершаются.

Скрипт начального bootstrap разрешён один раз в новой среде, принимает секрет только из секрет-хранилища или stdin, а не из аргументов процесса, и требует обязательной регистрации passkey до доступа к данным. В production его повторный запуск завершается ошибкой.

### 5.3. Права администраторов

Широкой роли `SUPER_ADMIN` нет. Разрешения задаются белым списком на сервере; начальные роли разделены по обязанностям:

| Роль | Разрешено | Запрещено |
|---|---|---|
| `PLATFORM_AUDITOR` | Обезличенные показатели платформы, системный аудит | Данные имущества, управление учётными записями, экспорт ПДн |
| `SUPPORT_OPERATOR` | Карточка организации, статус сервиса и контакты в объёме поддержки | Просмотр реестра ОС, изменение прав, массовый экспорт |
| `SECURITY_ADMIN` | Приглашение и блокировка администраторов, отзыв сессий, события безопасности | Данные организаций и биллинг без отдельного разрешения |
| `INCIDENT_RESPONDER` | Временный read-only доступ к конкретной организации по инциденту | Постоянный доступ, изменение хозяйственных данных, выдача ролей |

Доступ `INCIDENT_RESPONDER` создаётся для одной организации, с обязательной причиной, сроком не более 30 минут, аудитом открытия и закрытия. Для штатного случая он требует одобрения второго администратора; аварийный обход допускается только для заранее определённых инцидентов, сразу уведомляет ответственных и подлежит последующей проверке. Доступ не позволяет менять ОС, помещения, инвентаризации, пароль владельца или экспортировать весь tenant.

В первом выпуске админские роли назначаются только операционным процессом, а не интерфейсом. Это исключает самоназначение прав в непроверенной панели.

## 6. Авторизация и tenant-изоляция

### 6.1. Контекст пользовательского запроса

`requireUserAuth` выполняет последовательность:

1. проверяет, что путь вызван через пользовательский host и принимает только корректный access token типа `USER_ACCESS`;
2. проверяет подпись, `issuer`, `audience`, срок и `sid`;
3. загружает активные `Session` и `User`, проверяет статус и отзыв;
4. помещает в `req.auth` только `{ kind: 'user', userId, sessionId, organizationId }`.

`requireOrganizationContext` не читает `organizationId` из входа. DTO с этим полем отклоняется кодом `422`; сервисный слой во все операции передаёт `req.auth.organizationId` явно.

Для одиночного объекта запросы используют составной фильтр, например `where: { id: assetId, organizationId: ctx.organizationId }`. Для связанных сущностей проверяются обе стороны в одной транзакции. Prisma-ограничения и сервисные проверки не допускают связь объекта одной организации с объектом другой.

### 6.2. Контекст административного запроса

`requireAdminAuth` работает только на admin host, получает `AdminSession` из host-only cookie, проверяет её срок, бездействие, отзыв, состояние аккаунта и свежесть MFA. Затем `requireAdminPermission('...')` проверяет конкретное разрешение.

Ни `req.userId`, ни `req.adminId` не передаются клиентом. Отдельные Express router и отдельные middleware обязательны; нельзя строить middleware вида `if (user.isAdmin)` поверх пользовательской сессии.

## 7. Изменения модели данных

Целевая Prisma-модель из ТЗ дополняется следующими сущностями. Названия полей уточняются вместе с OpenAPI и миграцией, но смысл и ограничения обязательны.

| Сущность | Ключевые поля и ограничения |
|---|---|
| `User` | `organizationId` unique для этапа 1, `emailNormalized` unique, `passwordHash`, `status`, `emailVerifiedAt`, `consentAt`, `lastLoginAt`; пароль не выбирается в обычных `select` |
| `Session` | `userId`, `sessionFamilyId`, `tokenHash`, `secretVersion`, `expiresAt`, `revokedAt`, `replacedAt`, `replacedBySessionId`, `lastUsedAt`, ограниченные данные устройства; индекс `tokenHash` |
| `OneTimeToken` | `userId`, `purpose` (`EMAIL_VERIFICATION`, `PASSWORD_RESET`, `EMAIL_CHANGE`), `tokenHash`, `expiresAt`, `usedAt`; токен уникален и не хранится открыто |
| `ConsentRecord` | `userId`, тип и версия документа, `acceptedAt`, необходимые доказательства согласия; не заменяется простым boolean |
| `AdminAccount` | отдельный идентификатор, `emailNormalized` unique, `passwordHash`, `status`, `lastLoginAt`, `blockedAt`; нет связи с `User` |
| `AdminAccountRole` | `adminAccountId`, статическая роль, `assignedAt`, `assignedByAdminId`, основание назначения |
| `AdminWebAuthnCredential` | `adminAccountId`, уникальный credential ID, public key, sign counter, transports, даты регистрации и последнего применения |
| `AdminLoginTransaction` | `adminAccountId`, HMAC-хеш временного идентификатора и challenge, IP/UA в минимальном объёме, `expiresAt`, `usedAt`, лимит попыток |
| `AdminSession` | `adminAccountId`, HMAC-хеш cookie token, `authenticatedAt`, `lastUsedAt`, `expiresAt`, `revokedAt`, данные устройства в минимальном объёме |
| `AdminAuditEvent` | actor, действие, цель, результат, причина, request ID, время и ограниченные сведения об источнике; отдельная политика доступа и хранения |

Для random token используется HMAC-SHA-256 с отдельным секретом (`TOKEN_HASH_PEPPER`), а не быстрый неперчёсанный SHA-256. У записи есть версия секрета для контролируемой ротации. Пароли хешируются Argon2id отдельно и не зависят от token pepper.

`AuditLog` предметных действий сохраняется для tenant-сценариев согласно ТЗ. `AdminAuditEvent` не следует считать защитой от администратора, имеющего прямую запись в БД: значимые события дополнительно доставляются в защищённое централизованное хранилище логов с заданным сроком хранения.

## 8. API-контракт

### 8.1. Пользовательские маршруты

| Метод и путь | Результат |
|---|---|
| `POST /api/v1/auth/register` | Создаёт ожидающую подтверждения регистрацию; нейтральный `202` |
| `POST /api/v1/auth/verify-email` | Погашает одноразовый токен, активирует пользователя и создаёт сессию |
| `POST /api/v1/auth/login` | Создаёт session, устанавливает refresh cookie, возвращает access token |
| `POST /api/v1/auth/refresh` | Ротирует refresh token и возвращает access token |
| `POST /api/v1/auth/logout` | Отзывает текущую сессию и очищает cookie |
| `POST /api/v1/auth/logout-all` | Отзывает все сессии после повторной аутентификации |
| `GET /api/v1/auth/me` | Возвращает безопасный профиль и организацию текущего пользователя |
| `GET /api/v1/auth/sessions` | Возвращает список собственных сессий без token и лишней технической информации |
| `DELETE /api/v1/auth/sessions/{sessionId}` | Отзывает указанную собственную сессию |
| `POST /api/v1/auth/password-reset/request` | Нейтрально запускает письмо сброса |
| `POST /api/v1/auth/password-reset/confirm` | Меняет пароль и отзывает сессии |

### 8.2. Административные маршруты

| Метод и путь | Результат |
|---|---|
| `POST /api/admin/v1/auth/login` | Проверяет пароль, создаёт короткую login transaction и выдаёт WebAuthn challenge |
| `POST /api/admin/v1/auth/webauthn/verify` | Проверяет passkey и создаёт `AdminSession` |
| `POST /api/admin/v1/auth/logout` | Отзывает текущую admin session |
| `POST /api/admin/v1/auth/reauth` | Создаёт WebAuthn challenge для критичного действия |
| `POST /api/admin/v1/auth/reauth/verify` | Подтверждает свежую MFA для текущей сессии |
| `GET /api/admin/v1/auth/me` | Возвращает администратора и выданные разрешения |

Маршруты управления администраторами, аудита, организаций и инцидентов добавляются только после утверждения предметных требований и получают отдельные permission checks. Ответы не возвращают password hash, token, WebAuthn public key без потребности, полные IP-адреса или данные другой организации.

Все ошибки используют форму из ТЗ. Внутренние причины, stack trace, существование учётной записи и конфигурация не раскрываются клиенту. Все ответы auth используют `Cache-Control: no-store`.

## 9. Защита HTTP, браузера и инфраструктуры

### 9.1. Запросы и браузер

- В production пользовательский и административный SPA обращаются к API same-origin через reverse proxy. `CORS` для них не нужен. Если отдельный origin станет необходим, разрешается только точный allowlist без `*` и без сочетания `credentials: true` с wildcard.
- Cookie-аутентифицированные маршруты (`refresh`, `logout`, admin API) требуют точного `Origin`, проверяют Fetch Metadata и отклоняют неожиданные cross-site запросы. Unsafe user API использует bearer token в заголовке, а не cookie.
- Устанавливаются HSTS, CSP без `unsafe-inline`, `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, безопасная `Referrer-Policy`, ограничения `Permissions-Policy` и защита от clickjacking.
- Формы и ответы не содержат отражённый необработанный ввод. В UI не применяются `dangerouslySetInnerHTML` и не хранятся токены в `localStorage`, `sessionStorage`, IndexedDB или URL.
- Админ-хост получает собственную строгую CSP, не подключает сторонние скрипты аналитики и помечается `noindex` как дополнительная мера, не как средство защиты.

### 9.2. Ограничения и обнаружение атак

Лимиты настраиваются в production, применяются на reverse proxy по IP и на уровне приложения по идентичности/сессии. Первичные значения:

| Операция | Ограничение |
|---|---|
| Регистрация, повторная отправка, сброс пароля | 5 запросов за час на IP и 3 на email за час |
| Пользовательский login | 10 попыток за 15 минут на IP и 5 на нормализованный email |
| Refresh | 30 запросов за 5 минут на session и 60 на IP |
| Админский пароль и WebAuthn | 5 попыток за 15 минут на IP и на admin account |

При превышении возвращается `429` без раскрытия состояния аккаунта. Для паролей применяется прогрессивная задержка и временная приостановка, а не бессрочная блокировка, которую злоумышленник мог бы вызвать для чужого пользователя. Все значения являются конфигурацией, измеряются на пилоте и пересматриваются по событиям безопасности.

IP принимается только от явно доверенного reverse proxy. `trust proxy` не включается глобально без списка доверенных сетей, иначе клиент сможет подменять `X-Forwarded-For`.

### 9.3. Секреты, ключи и эксплуатация

- Заменяется единый `JWT_SECRET`: пользовательские ключи подписи access token хранятся в секрет-хранилище, имеют `kid`, отдельные `issuer`/`audience` и план ротации. Админский контур не использует этот ключ.
- Секреты HMAC для refresh и одноразовых токенов, SMTP-учётные данные, ключи WebAuthn и строки подключения передаются только через секрет-хранилище или защищённые переменные окружения. `.env.example` содержит имена и безопасные примеры без рабочих значений.
- Сервер отказывается запускаться в production без PostgreSQL, ключей, корректных origin, HTTPS-конфигурации и почтового канала. Mock mode допускается только при явном `APP_MODE=demo` вне production.
- PostgreSQL, резервные копии и транспорт до зависимостей защищаются шифрованием и сетевыми ограничениями. Доступ к БД не заменяет полномочия приложения.
- Логи содержат request ID, код результата и минимум диагностических данных. Email, IP, user-agent и иные ПДн маскируются или хранятся только на срок, утверждённый политикой хранения.

## 10. Клиентская реализация

Пользовательский frontend создаёт один API client:

1. access token находится в React state/памяти;
2. при `401` выполняется ровно один координированный `POST /auth/refresh` с `credentials: 'include'`;
3. после успеха повторяется только исходный безопасный запрос либо запрос с корректным idempotency-механизмом;
4. при неудаче состояние очищается и пользователь попадает на `/login` без сохранения token.

Админский frontend не получает token в JavaScript. Он использует same-origin запросы с `credentials: 'include'`; серверная `AdminSession` и permission checks определяют доступ. Любая страница админки загружает `GET /auth/me` и не показывает контент до подтверждения сессии и разрешения.

## 11. Порядок внедрения

1. Утвердить границу административного контура, набор реальных админских операций, владельцев ролей, почтового провайдера, сроков хранения и production-hosts.
2. Выполнить фазу 0 из плана: production-конфигурация, явный запрет mock mode, security headers, allowlist host/origin, request ID, единый формат ошибок и PostgreSQL-тестовый контур.
3. После подтверждённой миграционной стратегии создать целевую Prisma-схему: `Organization`, `User`, `Session`, tenant-сущности и таблицы этой спецификации. Миграцию с реальными данными предварительно проверять на копии БД и только с backup/rollback.
4. Реализовать и покрыть тестами пользовательскую регистрацию, email verification, Argon2id, login, rotation, logout, восстановление и `requireOrganizationContext`.
5. Защитить все предметные `/api/v1` маршруты и удалить возможность получить к ним доступ по одному факту заголовка `Bearer`.
6. Создать отдельный admin frontend, router, модели, WebAuthn и admin session; не переиспользовать demo-вход или пользовательский middleware.
7. Провести security review, интеграционные/E2E-тесты, проверку reverse proxy и ограниченный пилот до публичного запуска.

## 12. Критерии приёмки и проверки

До production должны проходить автоматические проверки:

1. Регистрация без `consent: true` отвечает `422` и не создаёт организацию, пользователя или сессию.
2. Неподтверждённый пользователь не получает access token и не читает tenant-данные.
3. Пароль, JWT, refresh token и токены подтверждения отсутствуют в БД в открытом виде, API-ответах, URL и логах.
4. Поддельный, просроченный, неверно подписанный, отозванный или с неправильным `iss`/`aud`/`typ` user token отвергается.
5. Refresh token можно применить один раз; его повторное применение отзывает всю family session.
6. Logout, password reset, блокировка пользователя и смена пароля немедленно прекращают соответствующие сессии.
7. Организация A не читает, не меняет, не экспортирует и не угадывает существование данных организации B; входящий `organizationId` отклоняется.
8. Пользовательский token не работает на `/api/admin/v1`, а admin cookie не принимается на `/api/v1`.
9. Администратор не завершает вход только по паролю: успешный WebAuthn с правильным challenge, origin, RP ID и UV обязателен.
10. Истёкшая, неактивная или отозванная `AdminSession` не открывает даже read-only admin endpoint.
11. Роль не даёт неразрешённое действие; временный incident access истекает и не позволяет изменять tenant-данные.
12. Cross-site запросы к cookie-маршрутам отклоняются; CORS не содержит wildcard с credentials.
13. Админские и пользовательские cookies имеют `__Host-`, `Secure`, `HttpOnly`, `SameSite=Strict`, host-only область и не пересекаются между хостами.
14. Конкурирующие refresh и WebAuthn-login запросы не создают две действующие сессии из одного одноразового артефакта.
15. E2E-проверки подтверждают, что frontend не сохраняет token в persistent browser storage и не использует демонстрационные URL как вход в рабочий контур.

Проверки tenant-изоляции из раздела 6 ТЗ остаются обязательными и дополняются этими проверками, а не заменяются ими.
